9. AI Review

How the AI part of the solution works, how well it serves the stated purpose, and how it could be improved without needing a bigger model or noticeably more processing. No code is shown. This review is based on static reading of the source; the application was not built or run on Spyre, so no measured timings or accuracy figures are claimed.

The capacity constraint behind every recommendation here. The documented platform runs one Granite 3.3-8B model on two Spyre cards with a 2,048-token context window (--max_model_len=2048) and at most 4 simultaneous requests (--max-num-seqs=4). Everything else (embeddings, chunking, text extraction, image models) runs on the s390x CPU of the backend container. Each suggestion below is therefore rated for how much extra work it adds:
NO EXTRA COST saves work or costs nothing   SMALL negligible CPU, no extra model calls   MODERATE extra model calls or storage, should be capped   AVOID not suitable for this platform

9.1  How the AI pipeline works today

The solution is a classic Retrieval-Augmented Generation (RAG) design: documents are cut into pieces and turned into numeric "fingerprints" (embeddings); at question time the pieces most similar to the question are fetched and given to the language model together with the question, so the model answers from the user's own material rather than from its general training.

StageWhat happensWhere it runsMain file
1. ExtractionText is read from PDF, DOCX, TXT etc.Backend CPUutils.py
2. SummaryThe start of the document is sent to the LLM to produce a summary, before the file is stored.Spyre (RHAIIS)rag.py, server.py
3. ChunkingText is cut into overlapping blocks of 25 lines (4 lines overlap).Backend CPUutils.py, config.py
4. EmbeddingEach chunk is converted to a vector by granite-embedding-278m-multilingual.Backend CPUopensearch_utils.py
5. IndexingVectors are stored in OpenSearch, one index per user (plus a separate one for images).OpenSearchopensearch_utils.py
6. Image handlingImages get a text caption (BLIP, with an attempt at a Granite Vision model first) and a CLIP embedding.Backend CPU (GPU if present)opensearch_utils.py (ImageRAG)
7. RetrievalThe question is embedded and the 5 most similar chunks are fetched; duplicates are removed. One image caption may be added.Backend CPU + OpenSearchopensearch_utils.py, server.py
8. Prompt buildingLanguage of the question is detected; the chunks and question are placed in a language-specific instruction ("answer only from the context").Backend CPUrag.py
9. GenerationThe prompt is streamed to Granite 3.3-8B at temperature 0.Spyre (RHAIIS)rhaiis_utils.py
Where Spyre is actually used: only stages 2 and 9 — the language-model calls. The solution documents describe Spyre as also accelerating extraction, chunking, embeddings and search; in the code those run on the ordinary CPU. That is a sensible choice for this platform (Spyre is dedicated to the large model), but it means the CPU side must be kept lean.

9.2  How well does this solve the intended purpose?

The stated purpose is to let users upload documents, get a role-appropriate summary, and then chat with their documents and get traceable answers.

Purpose elementHow the AI serves itVerdict
Answers grounded in the user's own documentsRAG with an "answer only from the context, otherwise say so" instruction and temperature 0.Good approach; sound foundation.
Private, per-user knowledgeSeparate OpenSearch index per user; retrieval can be restricted to chosen documents.Good (assuming user identity is trustworthy — see chapter 6).
Multilingual useMultilingual embedding model plus hand-written instructions for 7 languages.Good design, but summaries always use the English prompt because of the list-vs-string bug, and no multilingual testing exists.
Meaningful summariesOne LLM call on the first 16,000 characters of the document.Weak for long documents — everything after the start is silently ignored. The client cuts the prompt again to 10,000 characters.
Role-aware summaries (Admin/User)The role toggle exists in the UI but never reaches the prompt.Not delivered.
Traceable / cited answersSource file names are collected, but the final prompt builder drops the "Excerpt from <file>" labels, so the model never sees them and cannot cite.Not delivered (small fix).
Conversational chatEach question is answered on its own; no previous turns are sent.Follow-ups such as "and what about the second one?" will fail.
Image-aware answersImages are turned into captions; chat uses only the caption text.Works for simple "what is in this picture" cases; cannot read text or detail not present in the caption.
GuardrailsOnly the single "answer from context" instruction.No real guardrails; document text goes straight into the prompt (prompt-injection exposure).
Spyre accelerationLLM generation only.Appropriate, but over-claimed in the docs.

Strengths worth keeping

  • Temperature 0 and a "context only" instruction — right choice for factual document Q&A and for reproducible results.
  • A multilingual embedding model so a French question can find an English passage.
  • Streaming responses — the user sees the first words quickly even if the whole answer takes time.
  • De-duplication of retrieved chunks so overlapping text does not waste prompt space.
  • Document-scoped retrieval — the user can restrict a question to selected files.
  • A modest embedding model (278M parameters) — light enough for CPU; no need to change it.

9.3  Where the AI layer is weak

The biggest single mismatch: the prompt is sized for a much larger window than the platform has. The model is served with a 2,048-token window (roughly 1,500 English words, including the answer). The code allows prompts of up to 10,000 characters (about 2,500 tokens) and asks for up to 10,000 generated tokens. Five chunks of 25 lines plus an image caption can easily fill or exceed the window. When the limit is hit, the code cuts the prompt by characters from the end — which removes exactly the part that matters most: the question and the "Answer:" cue. The outcome would be a request rejected by the server or an answer to a half-read prompt.
#WeaknessEffectFiles
1Embedding model reloaded on every question (and on every ingest). The same happens to the CLIP image model for each upload, caption and chat request; the caption loader also first tries a heavier Granite Vision model before falling back to BLIP.Large avoidable CPU time and memory churn per request, with the s390x CPU doing the work; the main source of chat latency that has nothing to do with the LLM.opensearch_utils.py, server.py

3Chunking by 25 lines, not by meaning or size.A "line" can be a whole paragraph (PDF text) or a single word (tables). Chunks are then either enormous or meaningless, which harms both retrieval quality and the token budget. The documents promise "semantically meaningful" chunks.utils.py, config.py
4Whole document stored inside every chunk's metadata.Index size grows with (chunks × document size). A 100-chunk document is stored roughly 100 times over; wasteful for storage and for every search response.opensearch_utils.py
5Source labels removed before the model sees the context.No citations possible; the "traceable answers" claim is unmet.rag.py, server.py
6Fixed top-5 retrieval, no relevance threshold.Always returns five chunks even when none is relevant, so the model is fed noise; for broad questions five may be too few. Retrieval relies on vector similarity only, which is weak for exact names, codes and numbers.opensearch_utils.py, server.py
7No conversation memory.Follow-up questions retrieve and answer without context.server.py, rag.py, frontend chat tab
8Single-pass summary of the first 16,000 characters.Long documents are summarised from their start only, with no warning; and the summary is produced before the document is stored, so a slow model call delays the whole upload.rag.py, server.py

9.4  Improvements that fit the platform

The improvements are grouped by what they fix. All are changes to how the existing model and data are used. None needs a larger or additional language model, and several actually reduce the processing the system does today.

A. Make the existing work cheaper (do these first)

ImprovementWhat it meansBenefitCostFiles
A1. Load models once Create the embedding model and the CLIP/caption models once when the server starts (or on first use) and reuse them for all requests. Removes the repeated model loading from every chat turn, ingest and image upload. Frees CPU for real work and shortens answers noticeably, with identical results. NO EXTRA COST (saves CPU; one set of models stays in memory) opensearch_utils.py, server.py
A2. Store the document once Keep the full text in the document database (MongoDB already has it) and keep only the chunk text and a document reference in each index entry. Much smaller index, faster searches, lower OpenSearch memory use. NO EXTRA COST (saves storage) opensearch_utils.py
A3. Only search images when relevant Search the image index only when images are selected, or when the question mentions things like picture, photo, diagram, chart or screenshot (a simple word check, no model). Text questions skip a CLIP encode and a second search. Also avoids irrelevant image captions being added to the prompt and eating tokens. NO EXTRA COST server.py
A4. Drop the heavy captioning attempt Decide on one captioning model (BLIP is already the working fallback) and load only that. Avoids trying to load a much larger vision model on CPU, then discarding it. NO EXTRA COST opensearch_utils.py
A5. Quiet the logging Log timings, counts and sizes, not the full prompt and answer. Less I/O on every request and no confidential text in logs. NO EXTRA COST rhaiis_utils.py, server.py

B. Fit the prompt to the 2,048-token window

ImprovementWhat it meansBenefitCostFiles
B1. Token budget instead of a character cut Decide a budget: for example about 1,200 tokens for context, about 150 for instructions and question, the rest for the answer. Add chunks in relevance order until the budget is full; never cut the question. Set the answer limit to a realistic figure (a few hundred tokens), not 10,000. Requests always fit; the question is never lost; answers are predictable. A shorter maximum answer also frees the model's slot sooner for other users. SMALL (counting tokens with the model's tokenizer is cheap; an approximation is acceptable) rhaiis_utils.py, rag.py, config.py
B2. Chunk by size and structure Split at paragraph and sentence boundaries to a target of roughly 150–250 tokens with a small overlap; keep headings with their text; keep table rows together. Chunking is plain text processing and does not use any model. Retrieved chunks are coherent, similar in size and fit the budget; better matches for the embedding model. Delivers the "semantically meaningful chunking" the documents promise. SMALL (one-off at ingest; existing documents would need re-indexing) utils.py, config.py
B3. Use fewer, better chunks With a ~1,200-token context and ~200-token chunks, about 4–6 chunks fit. Keep k around 4, retrieve a few more candidates and then keep only those that pass a minimum similarity. Less noise in the prompt, fewer wrong answers, shorter prompts and faster first token. NO EXTRA COST opensearch_utils.py, server.py

C. Make answers better and traceable

ImprovementWhat it meansBenefitCostFiles
C1. Keep source labels in the prompt and return them Give each chunk a short tag such as "[1] report.pdf" in the prompt, ask the model to refer to them, and send the list of sources back to the UI next to the answer. Delivers the traceability promised in the documents; users can verify answers; hallucinations are easier to spot. SMALL (a few extra tokens per chunk) rag.py, server.py, frontend chat tab
C2. "Not found" path If no chunk passes the similarity threshold, answer immediately that nothing relevant was found, without calling the model. Avoids confident-sounding wrong answers and saves a full model call. NO EXTRA COST (saves a model call) server.py, opensearch_utils.py
C3. Hybrid search (keyword + vector) OpenSearch can combine ordinary keyword (BM25) scoring with the vector score in one query. No additional model is needed. Much better at exact names, IDs, part numbers, acronyms and figures, where pure vector search is weakest. Typical document Q&A needs both. SMALL (slightly heavier query on OpenSearch; nothing on the model side) opensearch_utils.py
C4. Short follow-up memory Carry the last one or two question/answer pairs (truncated) into the prompt within the token budget, or rewrite a follow-up into a standalone question using simple rules (for example, prepend the previous question's subject). Follow-up questions work; chat feels like a conversation. SMALL (prompt-only; use the standalone-rewrite via the LLM only if needed, as it adds a model call) server.py, rag.py, frontend chat tab
C5. Fence off retrieved text Wrap the context in clear markers and tell the model that anything inside is quoted material, not instructions. Put the instructions in a proper "system" message instead of a single user message. Reduces the chance a document steers the model; granite models respond better to a system/user split. NO EXTRA COST rag.py, rhaiis_utils.py
C6. Role-aware wording Add a short role clause to the summary and chat instructions (for example "technical administrator" versus "business user") and pass the role from the UI. Delivers the role-aware behaviour described in the solution template. NO EXTRA COST (a few tokens) rag.py, server.py, frontend

D. Summaries that cover the whole document, within a call budget

ImprovementWhat it meansBenefitCostFiles
D1. Fix the language choice Make the summary prompt actually use the detected language (the bug noted in chapter 6). Non-English documents get summaries in the right language. NO EXTRA COST rag.py
D2. Tell the user when a summary is partial Say in the result when only the first part of a long document was used. Honest output; nobody relies on a summary that missed 80% of the file. NO EXTRA COST rag.py, server.py, frontend
D3. Staged (map-reduce) summary for long documents Split the document into a few large sections, summarise each in a short call, then summarise the summaries. Cap the number of calls (for example at 4–6 sections; for longer documents sample evenly across the text) and run them one after another rather than all at once. Summary reflects the whole document, not just the start. MODERATE (several model calls per document instead of one) rag.py, server.py
D4. Summarise in the background / on demand Store and index the document first and generate the summary afterwards (or when the user clicks), instead of making the upload wait for the model. Uploads are fast; summary workload no longer competes with chat for the four model slots at the same moment. NO EXTRA COST (moves work, adds none) server.py, frontend

E. Protect the limited model capacity

ImprovementWhat it meansBenefitCostFiles
E1. Concurrency gate Allow at most a small number of in-flight model calls from the backend (for example 3, leaving one slot free for chat), queue the rest, and show "busy" instead of timing out after 5 minutes. Use a shorter timeout and a retry on the streaming path. Predictable behaviour under load; chat stays responsive when summaries are running. NO EXTRA COST rhaiis_utils.py, server.py
E2. Cache Cache query embeddings and the final answer for an identical question against the same documents; invalidate when documents change. Repeated questions (common in demos and review sessions) cost nothing. SMALL (a little memory) server.py, opensearch_utils.py
E3. Basic health and metrics Make the RHAIIS health check really call the model server; record time-to-first-token, tokens/s, queue length and retrieval time as counters. Operators can see whether slowness comes from CPU retrieval or from Spyre. SMALL server.py, rhaiis_utils.py

F. Know whether it works

ImprovementWhat it meansBenefitCostFiles
F1. Small evaluation set Keep 20–30 questions with expected answers or expected source passages on two or three sample documents (including a non-English one). Re-run after each change: did the right chunk get retrieved, was the answer correct, was the prompt within budget. The ROUGE helper already in the code can score summaries. Every improvement above can be shown to help (or not) with evidence. Prevents regressions. SMALL (run on demand, not in production) new test folder, rhaiis_utils.py metrics

Not recommended on this platform

IdeaWhy to avoid it
AVOID A larger or second language modelThe 8B model already needs two Spyre cards and the window is fixed at 2,048 tokens. A bigger model would not fit and is not needed; the weaknesses above are in how it is used.
AVOID A neural re-ranker on every queryA cross-encoder scoring many candidates on the s390x CPU would add seconds per question. Hybrid search (C3) plus a similarity threshold (B3) gives most of the gain at almost no cost.
AVOID Fine-tuning the modelNeeds data, hardware and time, and is not warranted until an evaluation set (F1) shows that prompt and retrieval changes are insufficient.
AVOID Larger embedding or vision modelsThe 278M multilingual embedder is a good balance for CPU. CLIP and BLIP are already the heavy part of the backend; make them load once (A1) rather than replace them.
AVOID Asking the LLM to rewrite every question, grade every chunk, or check every answerEach extra "AI helper" call consumes one of only four model slots. Use rules and thresholds first; add a model call only where evaluation proves the need.

Bottom line. The chosen AI approach (RAG over a modest model with a multilingual CPU embedder) is the right shape for this platform and for the stated purpose. The gaps are in the details: the prompt does not respect the model's 2,048-token window, the same models are reloaded for every request, citations and conversation history are missing, and long documents are summarised from their opening pages only. Steps 1 to 4 above can close most of those gaps while using less compute than the application uses today; only the optional staged summary adds model work, and that can be capped.
Basis of this review: static reading of the source, configuration and solution template. Estimates such as token counts, chunk sizes and budgets are sizing guidance, not measurements; they should be validated on the actual Spyre deployment with the evaluation set from item F1. No repository code was changed.
