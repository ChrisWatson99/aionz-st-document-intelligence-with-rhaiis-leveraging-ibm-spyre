8. Functionality Change Review

A plain-language guide to what must change and what could usefully change. No code is shown — each entry describes a piece of behaviour, the file(s) it lives in, and what effect the change would have. This review is based on static analysis; the application was not built or run.

Key:  MUST The application will not work correctly, or will fail to start, without this change.  OPTIONAL The application runs, but is misleading, fragile, or missing a stated feature.

Section 1 — Changes that must be made

These items stop the application from working as described, or introduce a correctness or security failure that makes it unsafe to demonstrate or deploy.

1.1  Python library imports will crash the server on startup

Severity: application does not start. Importing outdated module paths from LangChain causes Python to throw an error before the web server accepts a single request.
What the code does nowWhat it should doFiles affected
The backend uses import paths from LangChain v0.x (pre-2024). These paths were removed in v1.x, which is what a fresh install will pull in. Use the replacement paths that exist in current LangChain. The "Document" data type, the OpenSearch connector, and the embedding model loader all have new locations that are fully equivalent in behaviour. server.py, rag.py, opensearch_utils.py

1.2  Sentence-transformers and other packages are missing from the dependency list

Severity: silent failure at startup; embeddings and image analysis silently unavailable.
What the code does nowWhat it should doFiles affected
The packages that handle text embeddings, HTTP requests, PDF reading, image processing and score reporting are installed at container startup by a one-liner that ignores errors (pip install … || true). If any fail, the container continues and those features silently break. Every package the code imports must be listed in requirements.txt so that a failed install stops the build rather than producing a broken runtime. requirements.txt, docker-compose.yml

1.3  Multi-language summary detection always picks English

Severity: functional defect — every document is summarised in English regardless of its actual language.
What the code does nowWhat it should doFiles affected
When building a summary prompt the code runs a language-detection function that returns a ranked list (e.g. "probably English at 93%"). It then compares that entire list object against the string "fr", "de", etc. The comparison is always false, so English is always chosen. Read the top-ranked language from the list and compare that single value. This is exactly what the RAG chat path already does correctly — the fix is to apply the same logic in the summary path. rag.py — the summary prompt builder function

1.4  The RHAIIS health check always reports "healthy" and cannot detect a fault

Severity: operators cannot detect when the model server is down; all inference errors are masked.
What the code does nowWhat it should doFiles affected
The health-check endpoint in the backend has a hardcoded private IP address, makes no network call, and always returns "reachable: true". The error-handling code underneath it is dead code. Contact the RHAIIS server at the configured address (already available via an environment variable), call its status endpoint with a short timeout, and return the real result. If the server is unreachable, return an error that the UI can display. server.py — the health check endpoint

1.5  The RHAIIS model name, context window and port are inconsistent

Severity: requests to the model server will fail if the server is configured as documented, because the client sends the wrong model name and can exceed the context limit.
What the code does nowWhat it should doFiles affected
The solution template document says to start RHAIIS on port 8000 with a specific model identifier and a 2,048-token context window. The backend code connects to port 9000, uses a different model identifier, and sends prompts that can be up to 10,000 characters long — far exceeding the documented context window. Pick one configuration and make the code and documentation agree. The model name the client sends to RHAIIS must match the --served-model-name flag the model server is started with. The maximum prompt size must not exceed --max_model_len. If the port is 9000, document that. rag.py, rhaiis_utils.py, config.py, RHAIIS startup documentation in the solution template

1.6  No server-side authentication — anyone can read or delete any user's documents

Severity: data confidentiality failure. Any browser tab can impersonate any user.
What the code does nowWhat it should doFiles affected
The user's identity is a plain string supplied by the browser. The backend accepts whatever name the client sends and performs all database and index operations under that name. There is no login, no token, and no check that a request genuinely comes from the named user. Authenticate the user (even a simple shared-secret token or Basic Auth would close this gap for a demo). Derive the user identifier on the server side; never trust the client to supply it. server.py — all document and query endpoints; mongo_utils.py, opensearch_utils.py

1.7  CORS is open with credentials — allows cross-origin data theft

Severity: any website can make authenticated requests to the backend on behalf of a logged-in user.
What the code does nowWhat it should doFiles affected
The backend allows requests from any origin (*) and simultaneously allows credentials. This combination is forbidden by the browser specification and is a known security misconfiguration. Restrict allowed origins to the known frontend address. If it must be open for demonstration purposes, disable credential forwarding. server.py — the CORS configuration block

1.8  Uploaded files are written to a shared global temporary path

Severity: concurrent uploads from different users can overwrite each other; file names are attacker-controlled.
What the code does nowWhat it should doFiles affected
Every uploaded file is saved as /tmp/<original filename>. If two users upload a file with the same name at the same time, one overwrites the other. The original filename also controls the disk path, which can be manipulated. Create a unique temporary directory per upload, use an OS-generated temporary file name, and delete the file once processing is complete. server.py — the document upload endpoint

1.9  Frontend calls the wrong HTTP method on the user-check endpoint

Severity: a "user does not exist" error will appear every time the dashboard first loads in a browser.
What the code does nowWhat it should doFiles affected
The dashboard tries a GET request to check whether a user account exists. The backend only defines POST for that endpoint. GET returns HTTP 405 (Method Not Allowed). The frontend then falls back to POST, which works, but an error is logged every single time. Either use POST in the frontend from the start, or add GET support on the backend. frontend/src/components/Dashboard.js — the startup user check; server.py — the user-check endpoint

Section 2 — Changes that would be worthwhile

These items do not prevent the demo from running, but they close gaps between what the solution template claims the application does and what it actually does, and they make the application easier to operate and maintain.

2.1  Answers do not cite their sources

OPTIONAL The solution template describes traceable, cited answers. Currently the chat panel shows the model's response text only. The retrieved document chunks that informed the answer are never surfaced to the user.

What it would takeUser-visible benefitFiles affected
When the RAG pipeline retrieves chunks before sending a prompt, it already knows which document each chunk came from. That metadata can be forwarded alongside the answer to the frontend. Users see "Source: Annual Report 2023, page 4" beneath each answer, matching the product description. rag.py — RAG pipeline, server.py — the query endpoint, frontend/src/components/AIChatTab.js — answer display

2.2  Summaries are not role-aware

OPTIONAL The UI has an "Admin" / "User" toggle, and the solution template mentions role-aware summaries. The toggle is never sent to the backend and the summary prompt makes no distinction.

What it would takeUser-visible benefitFiles affected
The frontend already knows the selected role. Pass it with the summarise request. The backend can then choose a prompt that asks for a detailed technical summary (admin) versus a plain-language overview (user). Different users get summaries appropriate to their needs; the feature the template describes actually exists. rag.py — summary prompt builder, server.py — summarise endpoint, frontend/src/components/DocumentTab.js — summarise call

2.3  Text is split by line count, not by meaning

OPTIONAL The solution template describes "semantically meaningful chunking". The code splits documents into fixed 25-line blocks with a 4-line overlap. This approach cuts sentences and paragraphs in arbitrary places, which degrades retrieval quality.

What it would takeUser-visible benefitFiles affected
Replace the fixed-line splitter with a paragraph- or sentence-aware splitter. LangChain's recursive text splitter, which is already a dependency, does this and requires minimal change. Retrieved chunks are coherent units of text, so the model receives better context and gives more accurate answers. rag.py — the document chunking function

2.4  Chat history is stored in the browser with no expiry

OPTIONAL Conversation history for every session is written to localStorage. This data persists indefinitely in the browser, can be read by any script running on the same origin, and is never cleared server-side when a session ends.

What it would takeUser-visible benefitFiles affected
Store sessions on the server (in MongoDB, which is already running) and load them by session ID. This also means history persists across devices. Chat history is private to authenticated users, persists correctly, and is not exposed to browser storage risks. frontend/src/components/AIChatTab.js, server.py, mongo_utils.py

2.5  TLS verification is disabled when calling RHAIIS

OPTIONAL All HTTP requests to the RHAIIS model server are sent with SSL certificate verification disabled. This makes the connection vulnerable to interception.

What it would takeUser-visible benefitFiles affected
Enable verification and supply the CA certificate for the internal cluster (typically via an environment variable or a mounted secret). For a non-TLS RHAIIS endpoint, remove the flag rather than silencing the warning. Communication with the model server is authenticated, which matters in any environment beyond a developer laptop. rhaiis_utils.py

2.6  No content guardrails on model input or output

OPTIONAL The solution template mentions guardrails. The only safety mechanism currently present is a performance metrics printer. There is nothing to prevent a user from injecting instructions through an uploaded document that would alter the model's behaviour for other users.

What it would takeUser-visible benefitFiles affected
Add at minimum: a maximum input length check, content-type validation on uploaded files, and wrapping of retrieved text so that it is presented to the model as data rather than instructions. The application behaves predictably even with adversarial or malformed documents. server.py — upload endpoint, rag.py — prompt builders

2.7  Build and startup take a very long time because of source compilation

OPTIONAL The Dockerfile compiles PyTorch and Apache Arrow from source for the s390x architecture. This is the correct approach for a platform that lacks pre-built wheels, but it means a full build from scratch takes many tens of minutes and any dependency change forces a full recompile.

What it would takeUser-visible benefitFiles affected
Publish the compiled wheels to an internal registry and pull them during the Docker build. Alternatively, publish the compiled base image so only the application layer needs to be rebuilt on each change. Build times drop from hours to minutes for iterative development; the solution template's claim of a ~45-minute deployment becomes realistic. Dockerfile

2.8  The RHAIIS "Spyre acceleration" claim is not demonstrated in code

OPTIONAL The solution template states that Spyre accelerates extraction, chunking, embedding generation and vector search. In the code, only LLM inference (text generation) is sent to RHAIIS. Extraction, chunking and embedding all run on the application server CPU. Vector search runs in OpenSearch.

What it would takeUser-visible benefitFiles affected
Either: (a) add an embedding endpoint to the RHAIIS deployment and call it from the application instead of running embeddings locally; or (b) update the solution template to accurately describe what Spyre accelerates — which is solely LLM inference. The documented behaviour matches reality. Users and reviewers are not misled. opensearch_utils.py — embedding generation; solution template document

2.9  Dependency list is untidy and some packages are unused

OPTIONAL The requirements file contains packages that do not appear to be imported anywhere in the codebase. This makes builds slower, increases the image size, and creates a larger attack surface for supply-chain vulnerabilities.

What it would takeUser-visible benefitFiles affected
Audit imports against requirements.txt, remove packages that are not used, and pin all remaining packages to specific versions so builds are reproducible. Faster builds, smaller container images, and no surprise breakage when an upstream package releases a new version. requirements.txt

2.10  Documentation errors reduce usability and credibility

OPTIONAL Several documentation items are incorrect or inconsistent: the README links to a PDF that is actually a DOCX; the solution template references a different folder name than the actual repository; a command in the template contains a non-ASCII dash that will fail if copied; and the package name in package.json is still the scaffolding default ("my-app").

What it would takeUser-visible benefitFiles affected
Correct the link type in the README, align the folder name in the template, replace the en-dash with a regular hyphen, and set the package name to something meaningful. Someone following the documentation to set up the project will not hit confusing errors on the first attempt. README.md, solution template DOCX, frontend/package.json
